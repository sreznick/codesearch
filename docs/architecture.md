# План архитектуры

## Зачем всё это

Сейчас в репозитории уже есть несколько полезных кусков, но основная рабочая реализация находится в Java-ветке. Поэтому в рамках этой работы цель простая: не строить сразу большой кросс-языковый инструмент, а сделать Java-поддержку заметно лучше и чище внутри.

То, что уже сделано в `core`, лучше понимать не как попытку срочно смерджить все языки, а как способ перестать держать Java-код в одном монолитном слое.

## Почему стартуем от `main`

`main` сейчас самая понятная и стабильная база:
- там есть Java-реализация
- она хотя бы выглядит как цельный кусок
- там уже есть тесты

Это хорошо совпадает и с ответом преподавателя: как тема проекта развитие Java-поддержки выглядит сильнее, чем просто мердж нескольких веток между собой.


## Во что хотим прийти

В конце этой стадии проект должен выглядеть примерно так:

1. `core`
   Общие сущности и общая логика поиска, которые уже реально используются Java-частью.
2. `cli`
   Понятный вход для Java-сценариев.
3. `java`
   Чистый Java-модуль для индексации и поиска.
4. `storage`
   Работа с индексом Lucene.
5. `tests`
   Тесты на core, Java и CLI.

Если потом появится задача тащить сюда другие языки, эта структура уже не будет мешать. Но это следующий шаг, а не цель текущей ветки.

## Что уже стало общим

Внутри проекта уже начала появляться общая модель:

- `LanguageModule`
  Модуль, который умеет работать с конкретным языком.
- `CodeEntity`
  Любая сущность, которую мы хотим искать.
- `EntityKind`
  Тип сущности: класс, метод, поле, переменная, строковый литерал и так далее.
- `EntityLocation`
  Где именно это находится в коде.
- `SearchQuery`
  Не просто строка, а более осмысленный запрос.
- `SearchResult`
  Что именно нашли и как это показать пользователю.

Сейчас всё это нужно в первую очередь для Java. Если потом появится задача тянуть сюда другие языки, база уже будет готова.

## Что уже вынесли из legacy

Новый CLI больше не ходит за индексатором в `org.example`. Рабочая реализация индексации теперь лежит в `org.codesearch.java.JavaSourceIndexer`.

Старый `org.example.JavaSourceIndexer` пока оставлен как тонкая обертка. Это нужно, чтобы не ломать старый интерактивный CLI и legacy-тесты одним резким удалением.

При этом часть Java-разбора всё ещё зависит от `org.example`: там остаются сгенерированные ANTLR-классы и старые extractor-классы. Это нормально для текущего этапа. Следующий шаг — разбирать эти зависимости постепенно, а не пытаться переписать всё сразу.

## Ближайший план

Дальше порядок такой:

1. закрыть основные Java-сценарии поиска тестами
2. добавить ещё пару полезных Java-возможностей поверх текущего поиска
3. продолжить убирать дублирование между legacy Java-слоем и новым путём
4. постепенно перенести старые extractor-классы ближе к `org.codesearch.java`

## Что пока не делаем

Пока не трогаем вещи, которые могут занять много времени:
- UI
- сложный язык запросов
- ранжирование результатов
- агрессивную оптимизацию

Сначала нужен просто один нормальный, собираемый, понятный проект.

## Что хочется получить в конце этой стадии

Минимально хороший результат:
- один понятный Java CLI
- чистый внутренний путь индексации и поиска для Java
- поиск по именам сущностей и по declared type
- тесты на основные Java-сценарии
- документация, по которой можно поднять проект и показать результат
